Repository ruleset `require-ci-on-master` (id `19711116`) created via `gh api`: `target: branch`, `enforcement: active`, condition `ref_name.include: ["~DEFAULT_BRANCH"]`, one rule `required_status_checks` requiring context `verify` with `strict_required_status_checks_policy: false`, and `bypass_actors: [{actor_id: 5, actor_type: RepositoryRole, bypass_mode: always}]` (repository admin). Verified via `GET /repos/betancourtfit/ai-api/rules/branches/master`, which reports the rule applying to master with `checks: [{context: verify}]`; the create response reported `current_user_can_bypass: "always"`. **Corrected 2026-07-24 after an adversarial review — the original wording here overstated what this achieves.** With `bypass_mode: always` and the repository owner as the sole contributor, the ruleset blocks *nothing* for the person actually committing: the bypass applies to direct pushes AND to merging a pull request. Empirically, six commits — including the ones that modified `ci.yml` and the `Dockerfile` — landed directly on master after this ruleset was created, without a PR and without the check gating them.

So `verify` is an **informational signal, not a gate**: it turns red and tells you something broke, but nothing stops a red commit from reaching master. That is a deliberate, accepted trade-off for a single-developer personal repo — the friction of a mandatory PR workflow was judged not worth it here. It is recorded plainly so no future reader mistakes this for enforcement.

Note that "push freely + gate pull requests" is not an expressible configuration: a direct push carries a commit whose checks have not run yet, so any required status check necessarily rejects it. A real gate means a PR workflow. If that trade is ever revisited, the change is to drop the `bypass_actors` entry entirely.
