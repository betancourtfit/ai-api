<objective>
Close the Dockerfile/CI Bun version drift and add the CI job that keeps it closed.

The Dockerfile pins `oven/bun:1.1.29` in both stages. Bun 1.1.29 predates the text `bun.lock`
format (Bun v1.1.39+) and **silently ignores** this repo's lockfile — `bun install
--frozen-lockfile` exits 0 as a no-op and resolves from the `^` ranges in package.json instead.
The production image therefore ships `@cerebras/cerebras_cloud_sdk@1.91.0` and `groq-sdk@1.4.0`
while all 119 tests validate `1.64.1` / `1.2.1`.

Purpose: make the deployed image run the dependency set the test suite actually covers, and make
any future regression of that pin fail CI instead of failing silently in production.
Output: a Dockerfile on `oven/bun:1.3.11` (both stages), and a new `docker-image` job in the
existing CI workflow that builds the image on master and audits its installed dependencies
against `bun.lock`.

The new job:

- `needs: verify` — the image build compiles whisper.cpp and downloads 466 MB; do not spend ~15 min
  on it when the fast checks already failed.
- `if: github.event_name == 'push'` — the workflow triggers on push-to-master and on
  `pull_request`, so this expression means master-only. Skipped jobs do not block PRs, and this job
  is deliberately NOT a required status check.
- `runs-on: ubuntu-latest` (native amd64, matching the image's `--platform=linux/amd64`).

Steps, in order:

1. `actions/checkout@v7` — same floating major the `verify` job already uses.
2. `docker/setup-buildx-action@v3`.
3. `docker/build-push-action@v6`, named something like `Build production image`, with
   `context: .`, `platforms: linux/amd64`, `push: false`, `load: true`, `tags: bun-ai-api:ci`,
   `build-args: |` containing `CACHEBUST=${{ github.sha }}`, `cache-from: type=gha`, and
   `cache-to: type=gha,mode=max`. `load: true` is load-bearing and needs a comment saying so:
   with `push: false` alone the result stays in the buildx cache and never reaches the local docker
   daemon, so the next step's `docker run` would fail with "image not found". Use the floating
   majors `@v3`/`@v6` (not older pins) — they are what supports the current GitHub Actions cache
   service backend behind `type=gha`.
4. A run step named `Verify image deps match bun.lock`. This is the step that makes the whole job
   worth its runtime; write a comment above it explaining what it catches (Bun < 1.1.39 silently
   ignoring the text lockfile and resolving from `^` ranges, so `--frozen-lockfile` exits 0 having
   installed drifted versions). Also note there why the assertion lives here rather than as a `RUN`
   inside the Dockerfile: a CI-only assertion does not belong in the production image.

   Its shell, under the runner's default `bash`:
   - `set -euo pipefail`.
   - `docker run --rm --entrypoint bun bun-ai-api:ci pm ls > image-deps.txt`, then `cat` it so the
     raw listing is in the log. Overriding the entrypoint is what keeps `start.sh` (and the
     whisper-server sidecar) from launching; `WORKDIR /app` is inherited from the image.
   - Reduce the listing to bare `name@version` tokens with
     `sed -E 's/^[^A-Za-z@]*//'` (strips leading whitespace and the multi-byte tree-drawing
     prefix without depending on a UTF-8 locale) piped through
     `grep -E '^@?[A-Za-z0-9._/-]+@[0-9]'` (drops the `/app node_modules (N)` header and any Bun
     env-autoload notice) and `sort -u`. Suffix the whole pipeline with `|| true` so a no-match
     grep does not abort under `pipefail` before the guard below can report it.
   - **Anti-vacuous guard, mandatory:** if fewer than 5 tokens were parsed, emit a `::error::`
     saying the check parsed N packages and is therefore vacuous, and `exit 1`. Then assert the
     token list contains a line starting `@cerebras/cerebras_cloud_sdk@` and one starting
     `groq-sdk@`, each failing with its own `::error::`. Without these, a parsing change would turn
     the audit into a silent no-op — the exact failure mode this whole task exists to kill.
   - For each token, `grep -qF "\"$dep\"" bun.lock`. `bun.lock` stores every resolved package as a
     verbatim quoted `"name@version"` token, so a hit means the image installed exactly what the
     lockfile pins and a miss means it drifted. Print `OK   <dep>` on a hit; on a miss emit
     `::error::<dep> is installed in the image but is not the version bun.lock pins` and set a
     failure flag. Collect all mismatches in the loop and exit non-zero at the end rather than
     bailing on the first — one run should report every drifted package.
   - Finish with a success line naming the count.

   Deriving the expectation from `bun.lock` rather than hardcoding `1.64.1`/`1.2.1` keeps this step
   correct across future dependency bumps; the two name-presence assertions are what pin the check
   to the packages that actually matter.
